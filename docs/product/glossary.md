# Glossary

## Purpose

This glossary defines the language Recon should use consistently.

## Reconciliation as Code

A framework approach where reconciliation rules are defined in version-controlled files, run automatically, and produce evidence.

## Recon

The framework built by Recon Labs.

## recon-core

The first and central open-source repository/package. It contains the CLI, core framework model, contract parsing, check planning, result model, evidence generation, and extension interfaces.

## Equivalence contract

The core product object in Recon.

A versioned definition of how a source and target dataset should be compared.

A contract includes:

- source,
- target,
- grain / keys,
- columns or metrics,
- checks,
- tolerances,
- sampling,
- evidence,
- ownership.

## Source

The dataset or output used as the baseline for comparison.

A source can be:

- operational database table,
- warehouse table,
- view,
- query,
- old pipeline output,
- bronze/silver layer,
- previous business logic output.

## Target

The dataset or output being validated against the source.

A target can be:

- warehouse table,
- lakehouse table,
- replicated table,
- new pipeline output,
- gold layer,
- rewritten business logic output.

## Source-target equivalence

The condition where source and target match according to the equivalence contract.

Equivalence does not always mean byte-for-byte identical. It may allow:

- numeric tolerance,
- timestamp tolerance,
- known transformations,
- column normalization,
- expected row filtering,
- expected aggregation.

## Grain

The business level at which records are compared.

Examples:

- one row per customer,
- one row per order,
- one row per customer/month,
- one row per product/date.

## Key columns

Columns used to match source rows to target rows.

Recon should prefer business keys or canonical keys, not generated surrogate keys.

## Comparison identity

The row identity used to compare source and target outputs.

In contracts, comparison identity is declared with `grain.keys`.

The current design supports one default comparison identity per contract.
Optional named comparison identities are a future advanced-contract design.

## CDC identity

The identity used to validate CDC change propagation.

In contracts, CDC identity is declared with `cdc.keys`. It may be the same as
comparison identity, but Recon should not assume that silently.

The current design supports one default CDC identity per contract. Optional
named CDC identities are a future advanced-contract design.

## Surrogate key

A system-generated identifier, often different between source and target systems.

Recon should usually not compare surrogate keys directly unless the contract explicitly says so.

## Business key

A stable identifier meaningful across systems.

Examples:

- customer_external_id,
- order_number,
- policy_number,
- account_id + period.

## Check

An atomic reconciliation operation.

Examples:

- row count diff,
- missing keys,
- extra keys,
- aggregate sum diff,
- exact value match,
- numeric tolerance match,
- freshness lag.

## Check pack

A reusable group of checks.

Examples:

- basic equivalence,
- CDC equivalence,
- aggregate equivalence,
- medallion equivalence,
- finance controls.

## Sampling policy

A reusable definition of which records to compare.

Examples:

- deterministic hash sample,
- incremental/latest changed records,
- persisted random sample,
- previous failures,
- stratified sample.

## Tolerance policy

A reusable definition of acceptable differences.

Examples:

- currency tolerance of 0.01,
- timestamp tolerance of 5 seconds,
- percentage tolerance of 0.0001.

## Evidence

Artifacts generated by Recon to prove what was checked and what passed or failed.

Examples:

- terminal summary,
- JSON run result,
- CSV mismatch details,
- HTML report,
- result tables,
- future approval/sign-off report.

## CDC reconciliation

Continuous validation that a target system matches changes from a source system.

CDC reconciliation often uses watermarks, latest changed records, freshness lag, and insert/update/delete propagation checks.

CDC update and delete propagation checks usually depend on CDC identity, not only comparison grain.

## Watermark

A stored value, usually timestamp or offset, used to track incremental validation progress.

## Previous failure retest

A sampling strategy that always includes records that failed in recent runs.

## Medallion layer validation

Reconciliation across Bronze, Silver, and Gold layers.

## Parallel-run validation

Running old and new systems side-by-side and comparing their outputs before cutover.

## Adapter

A package or module that lets Recon connect to, inspect metadata from, execute
against, and render dialect-specific operations for a specific system.

Examples:

- `recon-snowflake`,
- `recon-postgres`,
- `recon-sqlserver`,
- `recon-bigquery`.

Adapters implement connector types.

## Connector

A user-facing connection configuration entry in a Recon profile.

Example:

```yaml
connections:
  warehouse:
    type: snowflake
```

Here `warehouse` is a connector name and `snowflake` resolves to an adapter
implementation.

## Typed check plan

The core-owned representation of what a compiled check should do before it is
rendered into dialect SQL or adapter execution requests.

Typed check plans keep comparison semantics in `recon-core` and let adapters
handle only system-specific rendering and execution.

## SQL renderer

An adapter-owned component that turns typed check plan operations into dialect
SQL for a specific system.

## Recon package

A reusable package containing check packs, sample policies, tolerance policies, macros, evidence templates, or examples.

## Recon Hub

Future community registry for adapters, packages, check packs, policies, and templates.

## Artifact

A generated output from a Recon run.

Examples:

- compiled SQL,
- run results,
- reports,
- failure details.

## Severity

The level of impact for a check result.

Possible examples:

- error,
- warn,
- info.

## Sign-off evidence

Reports or artifacts used by teams to approve a migration, refactor, CDC pipeline, or business logic rewrite.

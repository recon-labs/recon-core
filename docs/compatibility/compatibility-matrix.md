# Compatibility Matrix

## Purpose

This document records which Recon components are expected to work together.

Today the matrix is mostly a current-state record. Later it should become the
cross-repo compatibility source for `recon-core`, adapters, packages, the
adapter test kit, Hub metadata, and integrations.

## Current matrix

| Component or surface | Current version or status | Compatibility position |
| --- | --- | --- |

| Python runtime | `>=3.11` | Declared in `pyproject.toml`. |

| Contract schema stabilization | Planned | Schema freeze, machine-readable schema reference, deprecation lifecycle, and migration policy are gated before 1.0. |
| Named identities and multi-grain contracts | Planned | Current contract model supports one default `grain.keys` and one default `cdc.keys`; advanced identity roles are gated. |
| Manifest artifact | `artifact_version: 1` | Implemented for `recon parse`; pre-alpha compatibility. |
| Compiled contract artifact | `artifact_version: 1` | Implemented for `recon compile`; pre-alpha compatibility. |
| Compiled checks artifact | `artifact_version: 1` | Implemented for `recon compile`; pre-alpha compatibility. |
| Compiled SQL artifacts | Implemented for `recon compile --render-sql` | Current path is `target/compiled_sql/<contract_name>/<check_id>/<side_or_step>.sql`; compiled checks reference target-relative `compiled_sql/...` paths and include `rendering.adapter_type` when an adapter is known. A rendered check must have at least one SQL path. Empty renderer output, empty compiled SQL writer requests, and malformed rendered SQL writer requests are failures, not successful empty or misleading directories. Failed compiled YAML writes must not leave orphaned compiled SQL output or partial compiled YAML from the same invocation. |
| Generated artifact lifecycle and cleanup | Implemented for current compile outputs; gated for future outputs | Current manifest, compiled YAML, and compiled SQL writers reject unsafe paths and avoid stale, partial, or orphaned generated outputs. Batched artifact writers must validate the full batch and preflight all output paths before publishing the first directory or file; empty per-item output sets where success requires artifacts, invalid later entries, unsafe path segments, and case-insensitive output collisions must not leave partial generated artifacts. Future run results, evidence, failure details, reports, state, docs output, and selector-scoped artifacts must define cleanup and publish ordering before they become compatibility surfaces. |
| Artifact freshness and cache semantics | Planned | Cache optimization and skip-unchanged behavior are gated before generated artifacts can be reused silently. |
| Typed check plan | Draft typed operation catalog | Produced in compiled checks artifacts; current adapter-aware rendering renders current operations only and does not expand the catalog. |
| Check-pack invocation config | Strings and `{name}` mappings implemented; `config` and `on_empty` design locked by ADR 0018. | `config`, `on_empty: warn`, and `on_empty: skip` are not implemented yet. |
| Local custom check-pack resources | Planned | Local check-pack file schema, config schema, expansion, diagnostics, and artifact visibility are gated. |
| Local reusable policy resources | Planned | Local sampling, tolerance, and schema policy file schemas and reference resolution are gated. |
| Column and value comparison | Raw authored columns preserved; current typed column declaration/reference validation implemented under ADR 0019. | Row-level value checks, all-column expansion, resolved column metadata, eligibility enforcement, and adapter metadata validation are not implemented yet. |
| Tolerance, null, and normalization | High-level fields exist; MVP policy surface locked by ADR 0009. | Full typed resolver, reusable policy files, row-level execution, adapter rendering, results, and evidence are not implemented yet. |
| Endpoint resources and query execution | Planned | Endpoint refs and executable query endpoints are gated before implementation; current adapter-aware behavior is relation-only. |
| Selector readiness and subset execution | Planned in stages | `selectors.yml`, `--select`, `--exclude`, partial compile, and partial run are not implemented yet. MVP run-result and evidence surfaces should avoid whole-project-only assumptions. Early selector work should start with explicit contract/path scope for compile, SQL rendering, and run. `path:...` selectors should use project-relative manifest paths; exact file-path selection comes before directory-prefix selection. Named selectors, check-level selection, tag/domain/package selectors, state/result selectors, and rich composition remain later compatibility surfaces. |
| Sampling execution and stateful policies | Planned | Deterministic execution, anchor-side semantics, persisted samples, previous-failure samples, and multi-policy composition are gated. |
| CDC policy and delete semantics | Planned | First CDC execution, asymmetric delete representation, and advanced CDC modes are gated before implementation. |
| Semi-structured comparison | Planned | JSON path and semi-structured projection semantics are not implemented yet. |
| Profile and secret handling | Implemented for adapter-aware compile | Selected-target rendering, referenced-connection filtering, `{{ env_var(...) }}` and bare `env_var(...)` rendering for non-routing connection config, unsupported bare env-var expression rejection before adapter resolution, unsupported template-fragment rejection for `{{ ... }}`, `{% ... %}`, and `{# ... #}`, literal non-empty adapter `type` enforcement, templated `type` rejection before adapter resolution, factory-returned adapter metadata/profile `type` mismatch rejection before renderer selection, profile-backed adapter diagnostic suppression including adapter API compatibility and render-phase diagnostics, unsafe adapter-provided diagnostic code replacement, `rendering.adapter_type` redaction, non-string rendered-value redaction and unsafe config-key diagnostic-code redaction including key/value embeddings such as `RC_PASSWORD_LEAK`, `RCPASSWORDLEAK`, `RCsuper-secretLEAK`, and `RC12LEAK`, parsed DSN component and derived-fragment redaction, safe diagnostic-code preservation for incidental non-secret config-key substrings such as `RC_ADAPTER_CAPABILITY_UNSUPPORTED`, numeric `line`/`column` diagnostic fields, and short numeric rendered scalars such as port values in diagnostic codes, diagnostic text, unsafe resource metadata, and `rendering.adapter_type`, including integer-equivalent formatted variants such as `12.0`, `+12`, and `1.2e1`, and same adapter connection-context enforcement are implemented for `--render-sql`; run-time profile loading, debug/profile validation commands, and shared conformance tests are future work. |
| Adapter/Profile Diagnostic Conformance Gate | Required for future adapter/profile surfaces | Before adapter execution, profile/debug commands, run results, evidence, logs, shared adapter test-kit publication, `recon-duckdb` split, production adapter package publication, or external adapter compatibility claims, the matrix in `docs/compatibility/adapter-api.md` must be current and applicable rows must map to tests in core, the shared test kit, or the adapter repository. The gate requires literal adapter `type` routing, factory-returned adapter metadata/profile `type` mismatch rejection, unsupported template-fragment rejection for `{{ ... }}`, `{% ... %}`, and `{# ... #}`, field-by-field profile-backed adapter diagnostic redaction including DSN components and derived fragments, unsafe diagnostic-code suppression, safe public diagnostic-code preservation, explicit renderer binding checks before `render_plan()`, and explicit out-of-scope rationale for deferred execution surfaces. |
| Rendered SQL step capability enforcement | Implemented for current Core render-sql orchestration; gated for shared renderer/test-kit surfaces | Current Core `render_check_sql()` and `recon compile --render-sql` enforce `RenderedSql.required_capabilities` in addition to compiled check-plan requirements before compiled SQL is published. Before a shared renderer helper, renderer registry, adapter test kit, extracted `recon-duckdb`, production adapter package, or external adapter compatibility claim treats rendered SQL as compatible, conformance must preserve that invariant and cover unsupported, not-implemented, unknown, versioned, malformed, or extra step-level capability declarations before SQL artifacts, run results, evidence, or adapter test snapshots are published. |
| Renderer Output And Artifact Publication Conformance Gate | Required for shared renderer, test-kit, adapter, and future generated-artifact surfaces | Before a shared adapter test kit, extracted `recon-duckdb`, production adapter package, renderer registry, execution path, or external adapter compatibility claim treats rendered SQL or generated artifacts as compatible, `docs/compatibility/adapter-api.md` must map renderer-output and publication rows to tests. The gate requires non-empty renderer output, exported writer rejection of empty or malformed rendered SQL requests, batch rejection of later empty or malformed rendered SQL requests, malformed-output rejection, step-level capability enforcement, exact output non-file rejection, and all-or-nothing artifact publication before SQL artifacts, run results, evidence, reports, logs, snapshots, or state are published. Core owns filesystem publication safety; adapter repositories prove valid, capability-coherent renderer output and must not bypass Core preflight. |
| Source/target data privacy | Planned and gated by ADR 0022; current malformed YAML diagnostics suppress raw parser snippets | Before check execution, runner/results, evidence/reporting, failure details, debug commands, adapter execution, result/evidence sinks, result tables, or adapter test-kit compatibility claims can expose source/target data, Recon must apply the ADR 0022 privacy classification across terminal output, logs, diagnostics, run results, evidence, reports, failure details, result tables, adapter runtime errors, and test snapshots. Raw source/target rows, comparison keys, normalized values, diff values, query text, database errors, rendered profile values, credentials, and raw failure details are sensitive by default. Row counts, aggregate values, grouped keys, relation names, and source/target identifiers are policy-controlled before those surfaces are implemented. This gate applies to authored contract/config diagnostics when low-level parser errors can quote source/target query text, not only to runtime data. |
| Check engine boundary and result model | Planned first check-engine boundary | The first check-engine boundary owns the service boundary, in-memory check result model, locked status taxonomy, reason-code taxonomy, internal dispatch for already compiled checks, prerequisite/blocking representation, and diagnostic/result serialization shape. Check statuses are `pass`, `fail`, `warn`, `error`, `skipped`, `blocked`, and `not_executable`; aggregate run/contract statuses also include `no_checks`. `unsupported` and `not_yet_executable` are reason-code concepts under `not_executable`, not statuses. Empty compiled-check scope aggregates to `no_checks` and maps to command-level `RC_RUNTIME_NO_COMPILED_CHECKS`. Known later-phase operations use `not_implemented_in_current_phase`; unknown valid operation types use `unsupported_typed_operation`; malformed operation payloads are artifact-invalid diagnostics. It may reserve internal in-memory fields for future execution placement, required capability, artifact-reference, and sink-reference metadata, but must not implement adapter execution, generated `target/run_results.json`, evidence reports, failure details, result/evidence sinks, selectors, selected-scope outputs, or explicit authored `checks: [...]` support. Result-like public output remains pre-alpha and must not imply checks ran when execution is blocked, not executable, errored, skipped, or empty. |
| Adapter execution lifecycle and row count | Planned row-count execution phase | The row-count execution phase owns run-time profile loading for referenced connections, literal adapter type routing at execution time, adapter factory resolution and lifecycle, same-context DuckDB relation-backed execution, row-count execution, and sanitized adapter/runtime diagnostics. It is gated by Adapter/Profile Diagnostic Conformance, source/target privacy, and comparison execution placement. Query endpoints, cross-adapter execution, key-diff execution, aggregate execution, run-result artifacts, evidence, reports, and failure details remain out of scope. |
| Grain-key safety execution | Planned grain-key safety execution phase | The grain-key safety execution phase owns null source/target key checks, duplicate source/target key checks, missing key checks, extra key checks, and prerequisite/blocking semantics for dependent future row-level value checks. It must preserve locked key semantics: `grain.keys` is comparison identity, `cdc.keys` is CDC/change propagation identity, row-level checks require `grain.keys`, and sampling cannot bypass non-null or uniqueness requirements. Raw key export, row-level value comparison, CDC key execution, evidence reports, and failure details remain future gated surfaces. |
| Aggregate metric execution | Planned aggregate metric execution phase | The aggregate metric execution phase owns current ungrouped `sum_diff`, current grouped aggregate diff, numeric tolerance for supported numeric aggregate comparisons, empty aggregate semantics, and aggregate type-mismatch behavior. It is gated by comparison execution placement, typed operation catalog re-check, and source/target privacy. Timestamp/string tolerance execution, normalization/null-equivalence execution, schema policy execution, new metric catalog expansion, run-result artifacts, and evidence/report output remain future scope. |
| Adapter API | `ADAPTER_API_VERSION = "1"`, pre-alpha | No stable external adapter API release yet; current boundary separates `BaseAdapter` and `SqlRenderer`. |
| Capability catalog | Draft with ADR 0020 support states and ADR 0021/0022 future capability families | Support-state validation exists; the in-core DuckDB local adapter declares the current rendering subset. Execution placement, materialization/staging, and result/evidence sink-write capabilities are planned compatibility surfaces but not implemented. External adapters cannot claim broad execution placement, comparison-engine, staging, or table-sink compatibility until the relevant capability names, semantics, and adapter test-kit rows exist. |
| Adapter install extras and packaging strategy | `recon-core[duckdb]` implemented | The DuckDB local development adapter remains in-core; separate production adapter packages are future work. |
| Adapter packages | Planned | No official external adapter packages released yet; DuckDB starts in-core and `recon-duckdb` waits for adapter API and test-kit stability. |

resolution, including empty or malformed factory results, malformed factory diagnostic payloads including invalid `Diagnostic` field values, factories that return both adapters and diagnostics, | State backend | Planned | Local state is gated; remote/database-backed state has a separate gate before production use. |
| Hub and integration metadata | Planned | No Hub index, action, orchestrator, catalog, issue, or vault metadata contract exists yet. |

## Update rules

Update this matrix when any of the following change:

- supported Python versions,
- supported `recon-core` versions,
- contract schema compatibility,
- artifact schema versions,
- artifact freshness or cache semantics,
- typed check-plan versions or operation support,
- adapter API versions,
- adapter capability support,
- execution placement, comparison placement, materialization, or staging
  compatibility,
- probabilistic key-diff, Bloom/sketch, or approximate key-coverage
  compatibility,
- result/evidence sink modes, sink placement, sink requiredness, sink-write
  status, table schemas, or table migration compatibility,
- adapter test-kit compatibility,
- package resource compatibility,
- package lock or installer compatibility,
- official adapter, package, Hub, or integration release status.

If a new compatibility dimension appears later, add it to this matrix rather
than leaving it implicit.
